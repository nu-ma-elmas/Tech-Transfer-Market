# /spec

`docs/init-mvp-spec.md` §2を、人間との壁打ちで確定する。

このCommandは仕様を確定するだけであり、実装しない。実装は `/goal` の責務である。

## 正本

`docs/init-mvp-spec.md` が正本である。ここで判断基準を再掲しない。§2の項目、§3の実装ルール、`profiles/<selected_profile>/PROFILE.md` の制約に従う。

## 手順

1. **Preflight** — `git` / `gh` / `node` / `npm` が使えること、`gh auth status` が認証済みであることを確認する。満たさない場合は壁打ちを始めず、欠けているものと対処を報告する。
    - ここで確認するのは壁打ちに必要な範囲だけである。Working Treeの状態、npm各コマンドの実行可否、Profileの公開先、実行環境のTimezoneは、正本§4手順1が `/goal` の開始時に確認する。この手順はそれを代行しない。

2. **壁打ち** — §2の各項目を、人間との対話で埋める。
    - 一度に多く聞かない。1回の質問は3問までとする。
    - 人間が決めていない項目を、AIが埋めない。
    - 主要機能が3つを超えたら、超えた分をScope外へ移すよう促す。
    - Profileの制約に反する要望が出たら、その場で指摘し、適切なProfileへ案内する。`static-basic` に利用者の記録を残す必要が出たら `daily-local-app`、秘密Keyを要するAI処理が必要になったら `on-local-data-use-ai-app` を検討させる。
    - Server Database、認証、複数ユーザー、Device間同期、共有Record、保証されたBackupが必要になった場合は、**どのProfileの範囲でもない**。それはこのTemplateの対象外である。Scopeを削るか、別の基盤を選ぶかを人間に判断させる。

3. **曖昧箇所の一括抽出** — 手順2で§2の全項目の内容が揃ったら、`docs/init-mvp-spec.md` へ書く前にこの手順を行う。実装時に製品判断が必要になる箇所を全部洗い出し、人間にまとめて確認する。1件ずつ聞かず、まとめて聞く。実装中に停止して聞かなくて済む粒度になるまで、この手順を繰り返す。
    - **この手順を終えるまで手順4へ進まない。** 手順2の対話で個別に確認済みの項目も、ここで必ず一覧にして提示する。「手順2で聞いたから不要」と判断しない。この手順の価値は、逐次の対話で見落とした穴を、全項目を並べて見返すことで拾う点にある。
    - 洗い出した項目と人間の回答を、そのまま手順4で§2へ反映する。

4. **§2の書き込み** — 確定した内容を `docs/init-mvp-spec.md` §2へ書く。§1と§3以降は書き換えない。

5. **独立レビュー** — `independent-spec-reviewer` Subagentを起動する。あなたはこのレビューを代行しない。Verdictを上書き、再解釈、格下げしない。
    - `BLOCKED` なら、指摘された項目だけを手順2へ戻して直し、手順5をやり直す。やり直しは最大2周までとする。2周を終えてもなお `BLOCKED` なら、停止して人間に判断を求める。
    - `APPROVED` なら手順6へ進む。

6. **人間へ引き渡す** — `docs/spec-review.md` のVerdictを示し、人間に§1を `CONFIRMED` にするよう求める。
    - **あなたが§1を `CONFIRMED` にしない。** `CONFIRMED` にするのは人間だけである。
    - `CONFIRMED` になったあと `/goal docs/init-mvp-spec.md` を実行できることを伝えて終わる。

## 停止条件

`docs/init-mvp-spec.md` §6の停止条件に当たった場合は、続けず停止して人間に判断を求める。
